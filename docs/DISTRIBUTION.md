# Distribution checklist — quant-swarm

Ordered, credential-aware publish checklist for every distribution target.
**Do not publish out of order**: PyPI first (uvx and the registry metadata
both resolve against it), then everything else.

Naming discipline: the package is `**quant-swarm`** everywhere
(PyPI, uvx, MCP registry, Smithery slug `quant-swarm`).
`**quant-swarm-mcp**` remains the npm launcher name only.

---

## 0. Pre-flight (before any publish)

- [ ] `python -m pytest` green (includes `tests/test_registry_metadata.py` —
      `server.json` version must equal `pyproject.toml` version).
- [ ] Bump `pyproject.toml` version if the code changed, then re-run
      `python scripts/make_deeplinks.py` (Cursor artifacts) only if the stdio
      config shape changed.
- [ ] `python -m build` produces a clean wheel + sdist; `twine check dist/*`
      passes.

- Credential: PyPI API token for the `quant-swarm` project scope.
- [ ] `twine upload dist/*`

## Hosted endpoint verification (run before marking distribution "live")

These run against project `initiative-121-prod`, service `swarm-mcp`
(europe-west1). gcloud access required.

1. **Env on the service** (the code default also carries these hosts, so a
   clean deploy cannot silently 4xx every remote client):

   ```bash
   gcloud run services describe swarm-mcp --region europe-west1 \
     --project initiative-121-prod \
     --format='value(spec.template.spec.containers[0].env)'
   ```

   Confirm `SWARM_MCP_ALLOWED_HOSTS` — which now **extends** the in-code
   defaults (Cloud Run host + Smithery gateway + 1.21initiative.com) and can
   no longer lock out the Cloud Run hostname — and any
   `SWARM_MCP_REMOTE_URL`/`SWARM_MCP_TOKEN_VERIFY_URL`. If a custom domain is
   pinned, `SWARM_MCP_REMOTE_URL` is the advertised base. Note: the container
   access log is disabled (`access_log=False`) so query-string tokens never
   land in our log stream; Cloud Run still logs request URLs at the platform
   layer for Smithery-sourced calls (tokens are metered and revocable).

2. **Auth matrix** (record PASS/FAIL + timestamp per case):
   - [ ] Header auth: `POST <cloudrun>/mcp/data` with
         `Authorization: Bearer <token>` → initialize OK.
   - [ ] Query auth: same call with `?apiToken=<token>` and no header →
         initialize OK.
   - [ ] No token → 401 with the JSON-RPC unauthorized body.
   - [ ] Free token calling a Pro tool → 402 with `upgrade_url`.
   - [ ] stdio env-var path:
         `SWARM_MCP_ACCESS_TOKEN=<token> uvx --from quant-swarm swarm-data-mcp`,
         one `market.pulse` call → success.
   - [ ] Smithery-installed path: connect with `apiToken` set (works) and
         empty (tools list, access-required envelope on call).

## Site-side prerequisites (1.21.Initiative repo)

- [ ] Secret Manager (`initiative-121-prod`) contains `stripe-secret-key`,
      `stripe-webhook-secret`, `stripe-price-credits-10k`,
      `stripe-price-credits-100k`, and `stripe-metadata-enc-key` (base64,
      32 bytes — AES-256-GCM key that protects the raw token carried in
      Stripe session metadata for post-payment delivery), and the Cloud Run
      runtime SA can read them.
- [ ] The Stripe webhook endpoint is
      `https://1.21initiative.com/api/stripe/webhook` with
      `checkout.session.completed` enabled.
- [ ] A live test-mode checkout completes end-to-end and credits the token
      (email-first path: no pre-existing token — the buyer must receive the
      token email, which requires `stripe-metadata-enc-key` to be present).
- [ ] Remember: secrets are cached per instance — rotating one requires a
      **new revision** (touch an env var), not just a redeploy.

## Known issues (filed, not fixed in this cycle)

- `access.verify_entitlement` uses **sync** `httpx.post`
  (`swarm_mcp/access.py`) inside the async ASGI auth middleware — it blocks
  the event loop for up to 10 s on a cold verify. Convert to an async client
  (or run_in_executor) before the endpoint takes real remote traffic.
